# QA-08: 初回のスタンダードパーティ自動選出

## 目的

保存データがない初回利用時に、採用順位からスタンダードパーティの6体を用意する。メガシンカは最大2体とし、3体目以降のメガ候補は飛ばして順位の次候補を調べる。既存保存データや編集中のパーティを非同期取得で置き換えない。

## 調査結果

- 一覧 `/api` の `pokemon` は `summary.battleSummary.Current.Singles.position` を `UsageIndex.pokemon[].rank` として保持し、現在はrank順に並べている。採用率の割合を一覧からは受け取らない。
- `rank` がない行は `null`。未知の順位を上位扱いせず、選出候補から除外する。
- ローカル種族カタログは `Pokemon.mega` を持ち、`itemCatalog[].megaStone` が通常フォームからメガフォームへの対応を持つ。`pokemonAppearance(id, item)` で通常フォーム＋メガストーンを判定できる。
- `/api/battle/Singles/{id}` の `held_item` 行を含む詳細統計は `popularBuild` で合法性を検証して初期型に適用できる。詳細取得に失敗、または持ち物情報がない候補は通常フォームの既定型を使い、メガとは数えない。
- `App` は保存データがない場合も固定サンプルを返し、`saved` のmount時effectが直ちに保存する。これを抑止しないと、ランキング取得前に固定サンプルを保存して初回判定が失われる。
- パーティの保存時は重複持ち物を拒否する。順位候補そのものは残し、重複した持ち物を「もちものなし」にして保存可能な初期パーティを作る。

## 実装方針

- 初回利用は保存キーが存在しない場合だけとする。不正・読取不能な既存値も保存済みとして扱い、初回自動選出を行わない。
- 有効な正整数rankの候補だけを順位昇順で調べる。同順位は一覧に現れた順を保つ。ローカル未登録・同一フォーム・メガフォームと対応する通常フォームの重複は除外する。
- 候補の詳細を必要になった順位までだけ取得し、通常フォームの採用持ち物がメガストーンならメガ1体として数える。直接選択されたメガフォームも同じ上限に含める。3体目以降は採用せず、次順位へ進む。
- 6体を確保できない場合や一覧取得・検証に失敗した場合は、既存の初期サンプルをそのまま表示し、部分的に置き換えない。初回データは保存せず、次回起動で再試行できるようにする。有効な順位一覧があり詳細だけ不足する場合は、順位候補を既定型で採用する。
- 起動時に既存保存キーがないことを再確認してから一度だけ保存する。読み込み中にパーティ編集・選択・保存・読み込みを始めた場合は非同期結果を破棄する。編集後に既存パーティが変わっている場合も適用しない。

## 検証

- 順位順、rankなし、未登録・重複、直接メガ、通常フォーム＋メガストーン、3体目以降のスキップ、データ不足、持ち物重複の回帰テストを追加する。
- 非同期取得のキャンセル、既存保存値、編集済みパーティを保護する条件をテストする。
- `npm test`、`npm run typecheck`、`npm run format:check`（変更対象ファイル）、`npm run build`、`git diff --check` を実行する。
- 別の検証用originで Browser Use を行い、ランキング選出後の6枠・メガ数・順位・メガストーンを確認する。ユーザーの既存originの保存値は変更しない。
