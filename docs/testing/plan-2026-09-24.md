# テスト・改善実装計画書

作成日：2026-09-24。責任者：親エージェント（計画、配分、レビュー、受入）。
実装・テスト担当：TODO単位のGPT-6 Luna worker、推論max。

## 目的と範囲

現在のBATTLE NOTEについて、会話で承認された画面・計算・保存・行動候補が動作するかを確認し、発見した不具合を修正して再検証する。README、implementation.md、既存監査、今回までのブラウザコメントを照合元とする。トップページ、共通ヘッダー、説明文も対象。

公開デプロイ、新シーズンの追加、全ゲーム仕様の再現、全組合せの網羅、実機iOS/Android検証は今回の対象外。既存文書に明示された未対応計算と、新しく見つかった不具合は分けて記録する。外部API停止は成功扱いにせず、復旧・前回データ保持の動作と切り分ける。

## 実行ルール

1. 親は計画とTODOを管理し、実装は各workerに依頼する。モデル指定は起動APIの `gpt-6-luna` / `max` を根拠とする。起動エラーの場合は代替を使わず停止し、ユーザーへ報告する。
2. 各workerは担当ファイルを限定し、同じファイルの同時編集を避ける。失敗・不足は同じworkerへ再依頼する。合格するまでTODOを完了にしない。
3. 画面検証は親・workerともBrowser Use（mcp\_\_cua_repl）を使う。別のブラウザ操作ライブラリや直接CDPは使わない。
4. 保存操作を伴う画面検証は `http://127.0.0.1:5174/` の検証用オリジンで行う。5173のユーザーの保存データを上書きしない。検証用データにはQAと明記する。
5. ブラウザを使うworkerは1体ずつ動かし、操作競合を避ける。レスポンシブ確認は1435×987と390×844を基本にし、終了時に一時的なviewport指定を戻す。
6. 機能の不具合は再現条件・期待結果・実際の結果を記録し、必要な回帰テストを追加する。文章・軽微な装飾に実装をなぞるテストは追加しない。
7. 生成データを手編集しない。依存追加・公開・ブランチ・コミット・pushは行わない。既存未追跡ファイルをユーザーの作業として保護する。

## 合格基準

- G1：`npm test`、`npm run typecheck`、`npm run format:check`、`npm run build` が終了コード0。テスト件数と既知の警告を記録。
- G2：正解を独立に計算できるケースでは期待値を明示し、実装から期待値をコピーしない。境界、無効条件、異常入力を含む。
- G3：下記シナリオで操作が行き止まりにならず、画面と内部結果が一致する。未確認は未確認と記録。
- G4：PC・モバイルの主要画面で横はみ出し、読めない文字、操作不能、画像欠落がない。固定ヘッダー、ダイアログの閉じる操作、スクロールが使える。
- G5：保存失敗・重複・不正JSONで既存データを失わない。ページ移動後も保持すべき入力を維持する。
- G6：重大・高・中の発見不具合を未解決のまま合格にしない。軽微な既知警告や外部環境の制限は再現根拠付きで最終報告する。

## TODO別の具体的作業

### QA-01：既存検証の基準化

担当：qa_01_baseline。変更可能：検証レポートのみ。
4つの標準コマンドを実行し、検証開始時点の成否・テスト数・警告を記録。失敗した場合は親が対象を分類し、同じworkerへ最小修正を依頼する。
受入：G1、実行証跡を親が確認。

### QA-02：計算・回復・すばやさの回帰検証

担当：qa_02_calculations。対象：battle.ts、item-recovery.ts、speed.ts、speed-boosts.tsと対応テスト。
既存テストを確認し、不足している相互作用を重点的に検証する。ダメージのHP割合と一撃判定、0ダメージ、残HP、回復発動の閾値・消費回数・除去・無回復切替、複数ヒット、メガフォーム、すばやさランク・持ち物・特性の重複適用を対象とする。
既存の検証済み範囲を重複して膨らませず、具体的なリスクに対する回帰テストと必要な修正を行う。
受入：G1/G2。少なくとも境界と相互作用の検証根拠を提示。対象外の計算を新規実装せず記録する。

### QA-03：行動候補・判明情報・データ保存の整合性

担当：qa_03_predictions。対象：predictions.ts、usage.ts、data.ts、party-validation.tsと対応テスト。App.tsx/BattleFeatures.tsxの接続修正は親への通知後に行う。
過去監査A-01（控えの判明済み型の無視）・A-02（下降技の説明）を再判定。低採用率の未判明技が1位にならない、判明4技制約、未知の交代先、無効・ひんし除外を確認する。保存検証は不正入力、重複アイテム、空枠、なし、旧形式、日本語化を確認する。通信は既存のモックで日付・失敗・キャッシュ・未対応シーズンを確認する。
受入：G1/G2/G5。過去問題を未確認のまま「解決」としない。画面説明と実際の挙動が異なる場合は修正する。

### QA-04：画面操作・レスポンシブ・入力の検証

担当：qa_04_browser。ソース調査・手順準備のみ先行し、画面操作と修正はQA-02/03後。対象：UIコンポーネント・CSS・必要な入力ロジック。
Browser Useで次を検証する。

- トップ画像、ロゴのNOTE色、共通濃紺ヘッダー、各カードとナビ、使い方の開閉・新説明文。
- ダメージ画面：ポケモン選択、技変更、ポイントの先頭0除去・全角数字入力、ランク降順、攻守交換、回復切替、型比較の開閉、場・HP・技セット配置。
- パーティの呼び出し先を攻撃側/受け側に切替え、選択した側へ反映されること。
- すばやさ画面：初期の複数配分、配分絞込、適格な相手のみ+1/+2、検索、基準行への移動。
- 1435px・390pxのトップ、ダメージ、すばやさ、パーティ、説明ダイアログ。キーボードフォーカス、スクロールと閉じる操作。

IMEは全角文字の入力・正規化と実OS変換を区別する。Browser Useで実施できないOS IME変換を実施済みとしない。
受入：G3/G4。各シナリオの手順・観測結果・画面根拠をレポートに残す。

### QA-05：保存・重複警告・バックアップの画面検証

担当：qa_05_persistence。QA-04後、ブラウザ操作は引継ぎ。
5174上のQA用パーティで編集→保存→再読込を実施。同一アイテムを設定して保存拒否・具体的な警告・保存済み値維持を確認。重複解消後の保存、複数の「なし」、空枠を確認。JSON書出し→変更→読込み確認→復元と、不正JSONの拒否を検証する。ファイルはoutput/qa/内に置く。
受入：G3/G5。実UIと自動テストの両方で裏付け。5173の保存データは操作しない。

### QA-06：統合検証と文書の整合

担当：qa_06_integration。自動検証と文書整合は先行可能。全修正・画面検証完了後に最終判定。
標準4コマンドを再実行。worker修正が影響する画面のみBrowser Useで再確認。計画と成果物を突合して未検証事項・既知制限・警告を明記し、implementation.mdの古い説明を実装と一致させる。過去監査は歴史資料として維持し、最新の解決状況へリンクする。
受入：G1〜G6。親が報告と変更を検査し、必要に応じ同じworkerへ差し戻した後に最終判定。

## PDCAの記録方法

各レポートに、対象TODO、担当、変更ファイル、再現、期待/実際、実行コマンド、結果、未確認を記載。親はTODOリストのレビュー欄に初回判定・差戻し理由・再検証結果を追記する。追加の不具合は関連TODOへ追記し、範囲が独立する場合のみ新しいIDを付けて計画を更新する。

## 実行時の調整（2026-09-25）

workerのBrowser UseセッションからIABへ接続できなかったため、画面操作は親のBrowser Useで実施し、同じ担当workerが操作結果・DOM計測・画像を評価してレポート化した。実装修正は引き続き担当workerが行い、親がレビューした。Chromeの未完了のアクセス確認を回避する操作は行っていない。

保存検証は5174だけで実施し、実UIの書き出しファイルをそのまま読み込んで復元した。バックアップ形式の不正とJSON構文エラーの両方を拒否し、再読み込み後の保存値保持も確認した。容量不足などによるlocalStorage書き込み例外の実環境再現は未実施とし、重複による保存拒否と区別する。実OS IME変換・実機モバイル・ゲーム全組合せは検証済みとしない。

最終レビューでG5の書き込み例外境界を追加。QA-05の同じworkerが、依存を追加せず最小の保存関数とStorageのテストダブルで例外・既存値保持・保存禁止を検証する。Appへの接続変更後は親が通常保存経路をBrowser Useで再確認し、QA-06を再実行する。実際のブラウザ容量を強制的に使い切る試験と、自動テストによる例外検証は区別して報告する。
